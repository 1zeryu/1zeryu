# 故障沉淀闭环

## 什么时候用

- 修了一个「看起来很小、查了很久」的 bug。
- 同一个坑第二次出现（换了触发条件，或换了个模块）。
- 某个修复涉及多组件顺序，容易在下次部署时被破坏。

## 闭环的四步

```text
现象 → 根因 → 修复 → 验证
              ↓
        写入陷阱清单（一句话 + 后果）
              ↓
        同类问题再次出现 → 固化成 checklist / skill
```

只做到「修复」就结束，是这类项目最常见的浪费：同样的排查成本会被重复支付。

## 每步的最低要求

**现象**：写用户或监控能看到的事实。「GPU Pod 一直 Pending，熬到 1 小时后整条提交 failed」，不要写「调度有问题」。

**根因**：写到机制层，能解释为什么现象一定是这样。「VCI 实例创建失败在一次性要 4 卡时很常见，`fail-fast` 不再重试，所以 Pod 永久 Pending」。

**修复**：写改了哪个文件的哪个策略，以及为什么选它而不是替代方案。

**验证**：写可复现的观察。「3 份提交、12 个 GPU Pod 全 Succeeded、三条都 completed」，不要写「已修复」。

## 陷阱清单的写法

清单条目只保留两句：**症状 + 后果**，细节回链到维护日志。

```markdown
## 已知陷阱清单（改之前先读这一节）

1. 生成物边界：`app/common/` 由 `sync_common.sh` 生成，手改会在下次同步时被覆盖。
2. 部署顺序：`push → deps install → release`，跳过第二步会报 `No module named uvicorn`。
3. 配额维度：GPU 配额挂在「账号 × 地域 × 可用区 × 规格族」上，只换规格不换区解决不了 `ExceededQuota`。
```

注意第 3 条：它描述的是**约束**，不是某次事故；这种条目最值钱，因为能提前避免整类问题。

## 什么时候升级成 skill

满足任一条件就固化：

- 排查路径固定（先查 A，再查 B，最后查 C）。
- 涉及多处同步改动，漏一处就复发。
- 需要读多个文件才能还原上下文。

skill 里要写清「什么时候触发」和「改哪些文件必须一起查」，而不是复述这次事故。

## 反例

- ❌ 修复只进了 commit，没进陷阱清单——下次 AI 读代码看不出「这里为什么必须 fail-back」。
- ❌ 陷阱清单写成事故复盘长文——执行者需要的是「一句话 + 后果」。
- ❌ 把一次偶发环境问题写成通用陷阱——会造成过度防御。
