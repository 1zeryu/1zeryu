# AI 协作项目的维护日志

## 什么时候用

- 一个项目会持续几个月，中间要反复换会话、换人、换 AI。
- git 历史很薄（比如只有一次「initial commit」），提交信息解释不了设计取舍。
- 同一个坑被踩了第二次，但没人记得第一次怎么修的。

## 核心问题

AI 每次开新会话都是失忆的。它能读代码，但读不出三样东西：

1. **为什么这么设计**——代码只表达结果，不表达被否决的方案。
2. **哪里看起来能用其实不能用**——半迁移模块、历史遗留字段、已废弃接口。
3. **上次是怎么验证的**——没有验证记录，改动只能靠猜。

维护日志就是把这三样从会话记忆搬到仓库里。

## 写法

每条记录固定四段，缺一不可：

```markdown
### YYYY-MM-DD（一句话标题）

- **改了什么**：涉及的文件 / 模块 / 镜像 tag。
- **为什么**：触发问题（报错原文、线上现象、需求变化），以及否决了哪些替代方案。
- **怎么验证的**：具体命令、观察到的输出、在线上的哪个环境确认。
- **遗留**：没做完的部分、下次要注意的点。
```

三条硬规则：

- **写失败尝试**。只写成功路径的日志，下一个人会把失败方案再试一遍。
- **验证必须可复现**。写「验证通过」不算，要写「起了一次性 Pod 跑 `xxx`，输出 md5 与基线一致」。
- **改动当天回填**。拖到周末再写，只剩「改了若干文件」。

## 放在哪

- 单一文件按时间倒序，放 `docs/<项目>_operations.md` 的最后一节；文件过大时按季度拆。
- 和代码放在同一个仓库，一起 review、一起提交；不要放外部 wiki，否则 AI 读不到。
- 在 `AGENTS.md` 里写死一句：「每次改动都往 §7 追加一条」。没有这条约束，日志三个月后必然停更。

## 判断有没有用

三个月后问三个问题，都能在日志里找到答案才算合格：

1. 这个模块为什么不用现成的开源方案？
2. 这个字段为什么还在，是不是已经废弃？
3. 上次这个报错是怎么解决的？

## 反例

- ❌ 「优化了调度逻辑」——没说什么变了、为什么、怎么验证。
- ❌ 只有 commit message，没有文档——`fix bug`、`update` 这类信息量接近零。
- ❌ 日志写「已修复」但不写根因——下次换个触发条件就复发。
