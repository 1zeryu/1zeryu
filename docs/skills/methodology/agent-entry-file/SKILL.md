# 给 AI 的入口文件（AGENTS.md 模式）

## 什么时候用

- 一个仓库要交给 AI 反复改，而每次它都要重新摸索结构。
- AI 反复犯同一类错：改到生成物、漏做同步、把废弃模块当现行实现。
- 新人接手时，问的问题都集中在「先读什么」「哪些不能动」。

## 核心原则

入口文件不是 README。README 写给使用者，入口文件写给**执行者**，只回答四件事：

1. 先读什么，按什么顺序读。
2. 哪些事绝对不能做。
3. 改一个地方之后，必须连带同步什么。
4. 怎么判断这次改动没有把线上搞坏。

## 推荐结构

```markdown
# AGENTS.md — 给 AI agent / 新接手者的操作规矩

## 读序（按顺序，不要跳）
1. README.md — 仓库定位 + 哪套是线上
2. docs/<运维手册>.md — 落地事实 + §已知陷阱（动手前必读）
3. 架构总览 — 需要全局观时看

## 红线（违反会造成线上事故或数据泄漏）
1. 不修改 <旧开发栈目录> —— 仅参考
2. <敏感数据> 绝不外泄到数据库 / 公开层 / 参赛包
3. 不手改生成物 <生成物目录> —— 由 <同步脚本> 生成
4. 不硬编码 <清单类配置> —— 只存在于 <单一事实源文件>
5. 凭据不入库 —— 只从环境变量读
6. 不擅自跑远端 / 云上变更命令

## 常见改动 → 必做的同步
- 改 <A 目录> → 跑 <同步脚本>
- 改 <B> → 部署顺序固定为 <步骤 1> → <步骤 2> → <步骤 3>

## 落地前自检
- <自检命令 1>：检查什么
- <自检命令 2>：检查什么

## 改动后必须回填
- 每次改动往 <运维手册> 的变更历史追加一条

## 当前已知的「未完成 / 半迁移」状态（别被误导）
- <模块 A> 已迁移到 <新存储>，但 <模块 B> 仍在 <旧存储>
- <字段 C> 是历史遗留，改动前先确认当前落点
```

## 写法要点

- **用「不许」而不是「建议」**。AI 对祈使句的执行率明显高于形容词。
- **每条红线后面写清后果**（线上事故 / 数据泄漏 / 改动被覆盖），否则会被当成风格偏好。
- **同步映射写成表**，不要写成段落；AI 需要按「改了 X → 做 Y」查表。
- **专门写一节「半迁移状态」**。这是 AI 最容易读错的地方：代码里存在不等于线上在用。
- **入口文件保持在一屏到两屏**。超过 200 行就没人（和 AI）认真读；细节链接到 `docs/`。

## 维护

- 每次发现 AI 犯了新类型的错，就往红线或同步表里加一条，而不是在对话里口头纠正。
- 红线只增不减；确实失效的条目要删除并写进维护日志，别留着误导。
- 入口文件本身也要版本化，和代码一起提交。

## 反例

- ❌ 把架构设计、性能数据、路线图全塞进入口文件——执行者只需要约束，不需要愿景。
- ❌ 只写「注意不要改错」，不写「哪两个目录名字几乎一样、哪个是生成物」。
- ❌ 写了自检命令但没写预期输出，AI 无法判断是否通过。
