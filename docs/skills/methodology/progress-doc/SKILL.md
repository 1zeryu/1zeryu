# Agent 过程文档（Progress Doc）

## 什么时候用

- 任务有 3 步以上，中间要等命令、等下载、等用户确认。
- 用户明确表达「我要看过程」「每步告诉我到了什么结果」。
- 任务可能中断（断线、排队、换会话、换人），需要断点续跑。
- 多个 agent 或人并行做同一件事，需要对齐「现在到哪了」。

## 核心原则

文档是**唯一状态源**，不是事后总结。五条硬规则：

1. **计划先行**——没写进文档的步骤等于不存在，开工前先把步骤拆完写进去。
2. **一步一落**——每步结束立刻写，不攒到任务完；长命令执行前先把该步置 `in_progress`。
3. **证据优先**——写命令 + 关键输出 + 产物路径，不写「已处理」「已完成」。
4. **状态可 grep**——固定五种状态，任何人扫一眼就知道卡在哪一步。
5. **断点可续**——新会话只读这份文档就能接手，不依赖聊天记录。

## 放在哪

- 单任务：`docs/runs/<YYYY-MM-DD>-<task-slug>.md`；仓库已有约定目录就跟着走。
- 一任务一文件。多个任务共用一份会互相覆盖状态，监控价值归零。
- 和代码同仓库、随任务提交；不要放聊天记录或外部 wiki，agent 下次读不到。
- 任务结束不删：补完「结论」后归档；长期项目再把一句话摘要回填到 `maintenance-log`。

## 文档结构

```markdown
# <任务标题>

- 目标：<一句话，含可验收标准>
- 状态：in_progress
- 开始：2026-11-23 14:05
- 执行者：<人 / agent 会话标识>
- 产物：<最终文件或目录的绝对路径>

## 步骤总览

| # | 步骤 | 状态 | 结果摘要 | 更新时间 |
|---|------|------|----------|----------|
| 1 | 探测环境 | done | Python 3.11.4 / uv 0.4.18 | 14:06 |
| 2 | 安装依赖 | in_progress | | 14:09 |
| 3 | 跑通最小样例 | pending | | |

## 步骤详情

### 1. 探测环境 — done

- 做了什么：`python -V`、`uv --version`
- 结果：Python 3.11.4，uv 0.4.18
- 证据：命令输出即结果，无需落盘
- 下一步：装依赖

### 2. 安装依赖 — in_progress

- 做了什么：`uv add pandas pyarrow`
- 结果：
- 阻塞：

## 待确认 / 风险

- <需要用户拍板的点，以及不拍板时的默认选择>

## 变更

- <用户中途改需求时：改了什么、影响哪几步，不要静默改计划>

## 结论（任务结束时填）

- 达成：<逐条对照目标>
- 未完成：<遗留项 + 原因>
```

## 写法要点

- **状态只有五种**：`pending` / `in_progress` / `done` / `blocked` / `skipped`。不要自造「进行中」「基本完成」这类模糊词。
- **`blocked` 必须写清两件事**：卡在什么条件（缺权限、缺依赖、等确认），以及已经试过哪些方案、为什么失败。只写「失败了」等于没写。
- **结果摘要 ≤ 20 字，进表格**；细节进「步骤详情」。表格是给监控用的，详情是给复现用的。
- **证据三件套**：完整命令、关键输出（≤ 10 行）、产物绝对路径。整段构建日志不要粘，写到文件里再给路径。
- **每步写完顺手更新顶部「状态」和总览表**，别让顶部写着 `in_progress`、实际早就跑完了。
- **步骤要可验收**。「处理数据」不是步骤，「把 raw/*.jsonl 合并成 data.parquet 并核对行数」才是。
- **加步要说明**。中途冒出第 4 步，追加到总览表并写一句为什么加，别让计划悄悄变形。

## 用户怎么监控

- 看三处就够：顶部「状态」、步骤总览表、「待确认 / 风险」。
- 需要机器判断时，`grep -n "in_progress\|blocked" docs/runs/*.md` 直接定位卡点。
- agent 每完成一步，在对话里用一句话回报「第 N 步 done，结果 X」，文档负责留证，对话负责提醒。

## 和 maintenance-log 的分工

- **progress-doc**：单个任务的过程、证据、断点，任务结束即归档。
- **maintenance-log**：项目级、跨任务的变更历史，按日期倒序长期保留。
- 交接：任务结束时把「结论」压缩成一行回填维护日志，细节留在 progress-doc 里备查。

## 反例

- ❌ 全部跑完才补文档——中途一断就没有断点，文档退化成总结。
- ❌ 每步只写「已完成」「成功」——既不能复现，也无法判断是否真的通过。
- ❌ 把思考过程、试错流水账全写进去——用户要的是结果和证据，不是 transcript。
- ❌ 整段报错日志粘进文档——关键结论被淹没，反而更难监控。
- ❌ 任务结束不写「结论」、不更新顶部状态——下一个人接手时要重读全文才能还原结果。
